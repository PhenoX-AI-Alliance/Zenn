# Celeryワーカーにおけるシグナルハンドリングの実証実験：コンテナ環境でのSIGTERM安全停止の限界と設計指針

Kubernetesなどのコンテナオーケストレーション環境において、非同期タスクワーカーとしてCeleryを運用する際、Podのライフサイクル管理とタスクの整合性担保は避けて通れない永続的な課題です。特に、ローリングアップデートやオートスケーリングに伴う `SIGTERM` シグナルによる強制停止の際、実行中のバックグラウンドタスクが途中で断ち切られることで発生するデータ不整合や、ステータスの幽霊化（Ghost State）を防ぐための仕組みは、堅牢な分散システムを構築する上で不可欠となります。

私たち「結社（TOAI）」が推進する「命の地球プロジェクト」のバックエンド基盤においても、自律的に稼働する無数の非同期ワーカー群が、インフラの伸縮（スケールイン・アウト）に晒されながらもデータの純潔性を保ち続けることが至上命題でした。

本稿では、Celeryワーカーのグレースフルシャットダウン時に `worker_shutdown` シグナルと Pydantic / orjson を用いた高速な状態管理を組み合わせ、トランザクションの安全なロールバックと未完了タスクの再キューイングを実装する試みの検証結果と、そこから見えてきた**アーキテクチャ上の構造的限界**について、CTO視点での技術的考察を交えて共有します。

## 1. アーキテクチャと実装試案

本検証で設計したモジュールは、Celeryの遅延ACKメカニズム（`task_acks_late=True`）と、ワーカープロセス内のグローバル状態を監視するシグナルハンドラを統合したものです。

### なぜこの構成を選定したのか（技術的背景）
通常、Celeryワーカーはブローカー（RedisやRabbitMQ）からタスクを受け取った瞬間にACK（受信確認）を返します。しかし、このデフォルト挙動ではタスク処理中にPodが `SIGTERM` や `SIGKILL` で落とされた場合、タスクがブローカーから既に消滅しているため**「タスクのロスト（消失）」**が発生します。

これを防ぐため、以下の3つの設定を軸に設計を行いました。
1. **`task_acks_late=True`**: タスクの実行が完全に終了した後にのみACKを返すことで、強制終了時のタスク消失を防ぐ。
2. **`task_reject_on_worker_lost=True`**: ワーカープロセスが予期せず終了（`SIGKILL`等）した際、未ACKのタスクを自動的に再キューイングする。
3. **`worker_prefetch_multiplier=1`**: 各ワーカーがブローカーから先読み（Prefetch）するタスク数を1に制限し、シャットダウン時に道連れになるタスク数を最小化する。

さらに、高速なシリアライズ/デシリアライズを実現するため `orjson` を採用し、ペイロードの型安全性を担保するために `Pydantic` を組み込んでいます。

### 実装コード（環境依存・プロセスモデルの課題を残した検証版）

```python
import sys

# 必須ライブラリの事前チェック（Fail-Fast）
REQUIRED_LIBS = ["celery", "orjson", "pydantic", "redis"]
missing_libs = []

for lib in REQUIRED_LIBS:
    try:
        __import__(lib)
    except ImportError:
        missing_libs.append(lib)

if missing_libs:
    print(f"[ERROR] 以下の必須ライブラリがインストールされていません: {', '.join(missing_libs)}")
    print("以下のコマンドを実行して依存関係をインストールしてください:")
    print(f"    pip install {' '.join(missing_libs)}")
    sys.exit(1)

from typing import Any, Dict
from celery import Celery
from celery.exceptions import Reject
from celery.signals import worker_shutdown
import orjson
from pydantic import BaseModel, Field

# Celeryアプリケーションの設定
app = Celery(
    'secure_worker',
    broker='redis://localhost:6379/0',
    backend='redis://localhost:6379/1'
)

app.conf.update(
    task_acks_late=True,
    task_reject_on_worker_lost=True,
    worker_prefetch_multiplier=1,
)


class TaskPayload(BaseModel):
    task_id: str = Field(..., description="一意のタスクID")
    transaction_id: str = Field(..., description="トランザクションID")
    payload_data: Dict[str, Any] = Field(default_factory=dict, description="タスクのペイロードデータ")


class WorkerState(BaseModel):
    is_shutting_down: bool = Field(default=False, description="シャットダウンフラグ")
    active_transactions: int = Field(default=0, description="現在処理中のトランザクション数")


worker_state = WorkerState()


@worker_shutdown.connect
def on_worker_shutdown(**kwargs: Any) -> None:
    print("[Celery Signal] worker_shutdown シグナルが発火しました。シャットダウンフラグを有効化します。")
    worker_state.is_shutting_down = True


@app.task(bind=True, name='tasks.secure_process_task')
def secure_process_task(self, raw_json_payload: bytes) -> str:
    if worker_state.is_shutting_down:
        print(f"[Task] ワーカーシャットダウン中のため、タスク {self.request.id} を拒否します。")
        raise Reject(reason="worker_shutting_down", requeue=True)

    try:
        json_data = orjson.loads(raw_json_payload)
        payload = TaskPayload(**json_data)
    except Exception as e:
        print(f"[Task Error] ペイロードのバリデーションに失敗しました: {e}")
        raise

    worker_state.active_transactions += 1
    print(f"[Task] トランザクション開始: {payload.transaction_id} (Task ID: {payload.task_id})")

    try:
        if worker_state.is_shutting_down:
            print(f"[Task] 実行開始直後にSIGTERMを検知しました。ロールバックを実行します: {payload.transaction_id}")
            _rollback_transaction(payload.transaction_id)
            raise Reject(reason="worker_shutting_down_during_execution", requeue=True)

        _commit_transaction(payload.transaction_id)
        result = {"status": "success", "transaction_id": payload.transaction_id}
        return orjson.dumps(result).decode('utf-8')

    except Reject:
        _rollback_transaction(payload.transaction_id)
        raise

    except Exception as exc:
        print(f"[Task Error] エラー発生のためロールバックします: {exc}")
        _rollback_transaction(payload.transaction_id)
        raise exc

    finally:
        worker_state.active_transactions -= 1
        print(f"[Task] トランザクション終了処理完了: {payload.transaction_id}")


def _commit_transaction(tx_id: str) -> None:
    print(f"[DB] トランザクションコミット: {tx_id}")


def _rollback_transaction(tx_id: str) -> None:
    print(f"[DB] トランザクションロールバック: {tx_id}")
```

## 2. 遭遇した検証上の壁とアーキテクチャの限界

実際の運用環境を想定した検証およびQAプロセスを通じて、この「アプリケーション層でのシグナルハンドリング」には以下の技術的制約と設計上のトレードオフが存在することが明確になりました。

### 1. 実行環境とランタイムの依存性管理の乖離
初期検証段階において、スクリプト実行時に `ModuleNotFoundError: No module named 'celery'` が発生しました。これは、Pythonスクリプト内のコメントやドキュメントとしての依存関係記載が、ランタイム環境の自動プロビジョニングを保証しないという初歩的かつ重大な課題に起因します。
コンテナ環境（Docker/Kubernetes）においては、イメージビルド時（`Dockerfile`）またはCI/CDパイプラインでの明示的なパッケージ解決が不可欠であり、アプリケーションコード側での動的な `Fail-Fast` ガード（前述の `REQUIRED_LIBS` チェック）は、あくまで不親切なエラー出力を防ぐための補助輪に過ぎないことを再認識しました。

### 2. Celeryワーカープロセスモデルとメモリ空間の分離（最大の落とし穴）
Celeryはデフォルトで**プレフォーク（Prefork）プールモデル**を採用しており、親プロセス（MainProcess / Coordinator）の下で複数の子プロセス（Worker Process）がフォークされてタスクを実行します。

ここで発生する致命的な課題は、**Pythonのグローバル変数（本実装における `worker_state`）がプロセス間でメモリ空間を共有しない**という点です。
`worker_shutdown` シグナルは基本的に親プロセス側で捕捉されます。そのため、親プロセス内で `worker_state.is_shutting_down = True` に書き換えたとしても、既にフォークされて別メモリ空間で動いている各子プロセス（タスク実行コンテキスト）の `worker_state` にはリアルタイムに伝搬しません。

子プロセス側でシャットダウン状態を検知するには、`worker_process_shutdown` シグナルを併用するか、あるいはプロセス間通信（IPC）、共有メモリ（`multiprocessing.Value`）、もしくはRedis等の外部ストアを介した状態同期機構を挟む必要があります。インメモリフラグによる制御は、マルチプロセスモデルにおいては構造的な限界を抱えています。

### 3. 強制終了シグナル（SIGTERM）のタイムアウトとSIGKILLの壁
Kubernetesのポッド終了時、OSからの `SIGTERM` に対してCeleryワーカーは「Warm Shutdown（実行中タスクの完了待機）」を試みます。しかし、タスクが外部APIのI/O待ちや重いDBクエリなどのブロッキング処理を含んでいる場合、`terminationGracePeriodSeconds`（デフォルト30秒）の猶予期間内に処理が完了せず、最終的に `SIGKILL` によってプロセスが瞬断されます。

`task_acks_late=True` によりタスクの再キューイング自体は担保されるものの、`SIGKILL` が飛んだ瞬間、メモリ上で進行中だったトランザクションの確実なロールバック処理（`_rollback_transaction`）が実行されないままプロセスが消滅するリスクが残ります。
これに対処するには、アプリケーション層のシグナルハンドリングだけに頼るのではなく、以下のアプローチを併用するアーキテクチャ設計が必須となります。
- **データベース側のセッションタイムアウト設定**（放置されたコネクションとロックの自動解放）
- **分散ロック（Distributed Lock）とTTLによる有効期限管理**
- **タスク自体の冪等性（Idempotency）の担保**（再キューイングされて複数回実行されても結果が壊れない設計）

## 3. 知見と今後の設計方針

今回の検証を通じて得られた、実戦投入に向けた設計指針は以下の通りです。

1. **インメモリフラグによるシャットダウン制御からの脱却**:
   マルチプロセスで動作するCeleryにおいて、Pythonのグローバル変数を用いたトランザクション制御はプロセス境界を越えた正確な同期が困難です。状態管理はブローカーやRedis等の外部データストア、あるいはOSレベルのシグナル伝播に委ねるべきです。
2. **インフラストラクチャ層とアプリケーション層の責務分離**:
   `SIGTERM` への安全な追従は、アプリケーションコード内のシグナルハンドラだけに依存すべきではありません。Kubernetesの `preStop` フックを用いたグレースフルシャットダウンの誘導、`terminationGracePeriodSeconds` の適切な延長、そしてブローカー側の可視性タイムアウト（Visibility Timeout）のチューニングを組み合わせる必要があります。
3. **冪等性とOutboxパターンの採用**:
   分散システムにおいて「ワーカーが途中で死ぬこと」は前提条件です。シグナルで綺麗に止める努力と並行して、「いつ `SIGKILL` で落とされても、再実行時にデータの整合性が保たれる」冪等なタスク設計こそが、最も堅牢な防御策となります。
