プロダクトが成長し、数万・数百万のクライアントを抱えるようになると、インフラは「予期せぬトラフィックの暴力」に直面する。

その代表例が、プッシュ通知トリガーによるバックグラウンド同期、スリープ復帰時の一斉リクエスト、そしてネットワーク瞬断復帰時の「リフレッシュトークン再発行要求の同時殺到（Thundering Herd Problem）」だ。

OAuth2の認可基盤において、トークンの再発行エンドポイントは最も負荷が集中しやすく、かつ厳格なACID特性が要求されるクリティカルセクションである。我々が挑む「命の地球プロジェクト」の大規模自律分散インフラにおいても、エージェント群やクライアント端末から同一ユーザー識別子に対してミリ秒単位で再発行要求が突入し、データベースのコネクション枯渇、デッドロック、そしてトークンの二重発行（競合状態）という致命的な危機に直面した。

本記事では、この地獄のようなロック競合トラブルをいかにして構造的に解消したか、アーキテクチャ選定の背景から多層防御の実装、そしてシミュレーションによる検証結果まで、CTOの視点から詳細に共有する。

## 現場で何が起きていたのか：デバッグの軌跡と技術的考察

発端は、大規模な全体プッシュ通知を配信した直後に発生した監視アラートだった。
リレーショナルデータベース（RDB）のCPU使用率が100%に張り付き、スレッドプールが枯渇。APIゲートウェイの背後にある認可サービスからの応答が完全に途絶した。

エラーログには、次のような障害痕跡が連鎖していた。

```text
[ERROR] Database connection pool timeout or lock acquisition failed.
[ERROR] Deadlock found when trying to get lock; try restarting transaction
[WARN] Invalid or already revoked refresh token (Double-submit or race condition detected).
```

### 根本原因の技術的分析

1. **トークンローテーションの非アトミック性とRace Condition**
   RFC 6749およびOAuth 2.0 Security Best Current Practiceでは、セキュリティ向上のためリフレッシュトークンのローテーション（使い捨て再発行）が推奨されている。
   しかし、アプリケーション層で「旧トークンの存在確認（SELECT）」と「新トークンの保存および旧トークンの無効化（UPDATE）」を素朴に行っていた場合、数十スレッドが「同一の有効な旧トークン」を保持したまま同時に処理へ突入する。その結果、ほぼ同時に複数の新トークンが生成され、クライアント側とDB側でトークンの同期不整合（二重発行・即座の失効検知）が発生していた。

2. **悲観的行ロック（SELECT ... FOR UPDATE）への過信とコネクション枯渇**
   整合性を守るためにRDBの行ロック（`SELECT ... FOR UPDATE`）を導入した場合、同一レコードへの更新が集中すると、後続のトランザクションはロック解放を待機する。
   数千件のリクエストが同時に行ロックの獲得待ち行列に並んだ結果、データベースのコネクションプール（HikariCP / SQLAlchemy pool等）が瞬時に埋め尽くされ、他の読み取りクエリや無関係なマイクロサービスの通信まで巻き添えにしてシステム全体が停止した。

3. **「DBの手前」での調停の欠如**
   RDBは高信頼なストレージエンジンであるが、並行トランザクションの調停器（コーディネーター）として酷使すべきではない。DBに重い負荷がかかる前に、インメモリの高速なキー・バリューストアを用いてアプリケーション層でリクエストを直列化する仕組みが不可欠であった。

我々はこの課題を解決するため、**「Redis分散ロック」によるアプリケーション層での同一キー直列化・早期間引き**と、**「RDB悲観的ロック / トランザクション境界」による二重の安全弁**を組み合わせた多層防御アーキテクチャを採用した。

## 全体アーキテクチャ・シーケンス

```mermaid
sequenceDiagram
    autonumber
    participant Client as "クライアント群 (並行スレッド)"
    participant Redis as "Redis分散ロック"
    participant DB as "データベース (悲観的ロック)"

    Client -- "1. 分散ロック取得要求 (lock:refresh:{user_id})" --> Redis
    alt ロック取得成功 (先着1名)
        Redis -- "取得成功 (Acquired)" --> Client
        Client -- "2. トランザクション開始 & 悲観的ロック (SELECT ... FOR UPDATE)" --> DB
        DB -- "行ロック獲得" --> Client
        Client -- "3. トークン検証・新トークン生成" --> Client
        Client -- "4. UPDATE (旧トークン無効化 & 新トークン保存) & COMMIT" --> DB
        DB -- "処理完了" --> Client
        Client -- "5. 分散ロック解放" --> Redis
    else ロック取得失敗 (後続リクエスト)
        Redis -- "タイムアウト / 拒否" --> Client
        Client -- "早期リターン (HTTP 429 Too Many Requests)" --> Client
    end
```

### アーキテクチャの選定理由
- **ユーザー単位のキー粒度**: 全体ロックではなく `lock:refresh:{user_id}` の粒度で分散ロックをかけることで、他ユーザーの処理には一切影響を与えず、同一ユーザーの重複リクエストのみをピンポイントで直列化する。
- **Fail-Fast設計**: ロック待機タイムアウトを短く設定（数ミリ秒〜数百ミリ秒）し、獲得できない後続リクエストはDBに触れさせることなく直ちにHTTP 429（または直前キャッシュ結果の返却）で処理する。
- **多層防御（Defense in Depth）**: 万が一Redisクラスタのフェイルオーバーやネットワーク分断でロックが二重取得された場合でも、背後のDB側でトランザクション境界とバージョンチェックを行うことで、データの不整合を100%防止する。

## 実装：高負荷に耐える堅牢なトークン再発行サービス

以下は、上記の多層防御メカニズムを検証するために構築した堅牢な実装コードである。
Pydantic v2による厳格なバリデーション、高速シリアライズ、およびマルチスレッドによる並行実行シミュレータを内包している。

```python
import time
import threading
from typing import Optional
from concurrent.futures import ThreadPoolExecutor, as_completed

# orjson のフォールバック実装（堅牢性の向上）
try:
    import orjson
    def json_dumps(obj):
        return orjson.dumps(obj)
    def json_loads(data):
        return orjson.loads(data)
except ImportError:
    import json
    def json_dumps(obj):
        return json.dumps(obj).encode("utf-8")
    def json_loads(data):
        return json.loads(data.decode("utf-8") if isinstance(data, bytes) else data)

from pydantic import BaseModel, Field

# ---------------------------------------------------------
# Pydantic (v2) スキーマ定義
# ---------------------------------------------------------
class TokenRefreshRequest(BaseModel):
    user_id: str = Field(..., description="ユーザー識別子")
    refresh_token: str = Field(..., description="リフレッシュトークン文字列")

class TokenRefreshResponse(BaseModel):
    access_token: str
    refresh_token: str
    expires_in: int
    status: str

# ---------------------------------------------------------
# モック: Redis分散ロックおよびデータベースのシミュレータ
# ---------------------------------------------------------
class MockRedisLock:
    """Redis分散ロックのシミュレータ（Redlockの概念を模倣）"""
    def __init__(self):
        self._locks = {}
        self._global_lock = threading.Lock()

    def acquire(self, key: str, timeout: float = 3.0) -> bool:
        start_time = time.time()
        while time.time() - start_time < timeout:
            with self._global_lock:
                if not self._locks.get(key, False):
                    self._locks[key] = True
                    return True
            time.sleep(0.01)
        return False

    def release(self, key: str):
        with self._global_lock:
            self._locks[key] = False

class MockDatabase:
    """DBの行ロック競合およびトランザクションを模倣するクラス"""
    def __init__(self):
        self._db_locks = {}
        self._global_lock = threading.Lock()
        # モックのユーザー別トークン状態
        self.tokens = {
            "user_1001": {"current_token": "valid_refresh_token_abc", "version": 1}
        }

    def execute_refresh_with_pessimistic_lock(self, user_id: str, old_token: str) -> TokenRefreshResponse:
        """
        SELECT ... FOR UPDATE と短いタイムアウトを模倣した悲観的ロック処理
        """
        lock_wait_start = time.time()
        while True:
            with self._global_lock:
                if not self._db_locks.get(user_id, False):
                    self._db_locks[user_id] = True
                    break
            if time.time() - lock_wait_start > 1.0:
                raise TimeoutError("Database connection pool timeout or lock acquisition failed.")
            time.sleep(0.01)

        try:
            # トランザクション開始 (BEGIN)
            user_data = self.tokens.get(user_id)
            if not user_data or user_data["current_token"] != old_token:
                raise ValueError("Invalid or already revoked refresh token (Double-submit or race condition detected).")

            # トークンの更新処理
            new_access_token = f"acc_{time.time_ns()}"
            new_refresh_token = f"ref_{time.time_ns()}"
            user_data["current_token"] = new_refresh_token
            user_data["version"] += 1

            # コミット (COMMIT)
            return TokenRefreshResponse(
                access_token=new_access_token,
                refresh_token=new_refresh_token,
                expires_in=3600,
                status="success"
            )
        finally:
            with self._global_lock:
                self._db_locks[user_id] = False

# ---------------------------------------------------------
# OAuth2 トークン再発行サービス層
# ---------------------------------------------------------
class OAuth2TokenService:
    def __init__(self, redis_lock: MockRedisLock, db: MockDatabase):
        self.redis_lock = redis_lock
        self.db = db

    def refresh_token(self, request_json: bytes) -> bytes:
        """
        1. Pydanticでリクエスト検証
        2. Redis分散ロック取得（同一ユーザーへの同時書き込み直列化）
        3. DB悲観的ロックによる安全なトランザクション実行
        4. シリアライザによる高速シリアライズ
        """
        req_dict = json_loads(request_json)
        req = TokenRefreshRequest(**req_dict)

        lock_key = f"lock:refresh:{req.user_id}"
        
        # Redis分散ロックの取得（タイムアウト付き）
        acquired = self.redis_lock.acquire(lock_key, timeout=2.0)
        if not acquired:
            err_res = {"error": "locked", "message": "Concurrent request limit reached for this user."}
            return json_dumps(err_res)

        try:
            # DB側での排他制御付き処理（トランザクション境界）
            response = self.db.execute_refresh_with_pessimistic_lock(req.user_id, req.refresh_token)
            return json_dumps(response.model_dump())
        except (ValueError, TimeoutError) as e:
            err_res = {"error": "conflict_or_invalid", "message": str(e)}
            return json_dumps(err_res)
        finally:
            # データベースの永続化・状態更新が完全に完了した後にのみロックを解放する
            self.redis_lock.release(lock_key)

# ---------------------------------------------------------
# 検証用CLIシミュレータ
# ---------------------------------------------------------
def simulate_concurrent_requests():
    redis_lock = MockRedisLock()
    db = MockDatabase()
    service = OAuth2TokenService(redis_lock, db)

    target_user = "user_1001"
    initial_token = "valid_refresh_token_abc"

    print(f"[*] シミュレーション開始: ユーザー '{target_user}' に対して同時に複数のトークン再発行リクエストを送信します。")

    concurrency = 50
    success_count = 0
    error_count = 0
    lock_block_count = 0

    def worker():
        nonlocal success_count, error_count, lock_block_count
        req_data = TokenRefreshRequest(user_id=target_user, refresh_token=initial_token)
        json_payload = json_dumps(req_data.model_dump())

        result_bytes = service.refresh_token(json_payload)
        res_dict = json_loads(result_bytes)

        if "status" in res_dict and res_dict["status"] == "success":
            success_count += 1
        elif res_dict.get("error") == "locked":
            lock_block_count += 1
        else:
            error_count += 1

    with ThreadPoolExecutor(max_workers=concurrency) as executor:
        futures = [executor.submit(worker) for _ in range(concurrency)]
        for future in as_completed(futures):
            future.result()

    print("\n--- 検証結果レポート ---")
    print(f"総リクエスト数: {concurrency}")
    print(f"成功（最初の一件）: {success_count}")
    print(f"分散ロックによりブロックされた要求数: {lock_block_count}")
    print(f"競合エラー（二重発行阻止）: {error_count}")
    
    # アサーションによる検証担保
    assert success_count == 1, f"異常検知: 二重発行または複数成功が発生しています (success_count={success_count})"
    print("\n[検証成功] Redis分散ロックとDB悲観的ロックにより、競合と二重発行が確実に抑制されました。")

if __name__ == "__main__":
    simulate_concurrent_requests()
```

## 考察と実践的な教訓

大規模分散システムにおいて、同時実行性（Concurrency）とデータの整合性の両立は極めて繊細なエンジニアリングが要求される。
今回の知見から導き出される重要な原則は以下の通りである。

1. **RDBに同時実行制御の全責任を背負わせない**
   行ロックは強力だが、リクエスト集中時の待機コストとコネクション枯渇リスクが高い。手前の分散キャッシュ層（Redis等）でリクエストを直列化し、不要なトランザクションをFail-Fastに排除することがDB保護の鍵となる。
2. **多層防御の原則**
   Redisの分散ロックがクラスタ障害等で万一突破されたとしても、DB側のトランザクションとバージョン照合が最終防衛ラインとして機能しなければならない。単一障害点を作らない設計こそが堅牢性を生む。
3. **テスト駆動による競合検証**
   並行処理のバグは通常の単体テストでは顕在化しない。マルチスレッドや負荷試験ツールを用いたレースコンディションの再現環境をコード化し、継続的にアサーションを行う体制を築くことが不可欠である。
