24時間止めることのできない高頻度トランザクションを扱うSaaS事業者にとって、本番稼働中の非同期マイクロサービス（FastAPI / asyncio）における予期せぬランタイム例外は致命傷です。

近年、「AIがコードを全自動で完璧に直してくれます」と謳うツールが溢れています。しかし、非同期ランタイムの裏側で、LLMにコード全体を勝手に書き換えさせる行為がどれほど危険な賭けであるか、現場のシニアエンジニアなら痛いほど理解しているはずです。

私たちはこの幻想的な「全能の魔法」を捨てました。Python標準の `ast` モジュールによる確定的なルールベース置換を主軸とし、ローカルLLMは最小限の文脈推論に留める「安全第一」のアーキテクチャをご紹介します。

## なぜAST（抽象構文木）による確定的置換なのか？

非同期環境下でのコード動的修復において最も重要なのは「予測可能性」です。LLMによる文字列ベースの置換は、インデントの崩れや予期せぬ変数のシャドウイングを招きかねません。

一方、Pythonの `ast` モジュールを使用すれば、コードを木構造としてパースし、目的のステートメントのみを安全に `ast.Call`（`.get()` メソッドの呼び出し）へ確定的・局所的に変換できます。

### コアコンポーネント：例外インターセプターとASTパッチ

システムは主に3つの層で構築されています。
1. **Exception Interceptor**: `asyncio` のイベントループ上で発生した未処理例外をフックし、スタックトレースからコンテキストをキャプチャ。
2. **AST Inspector**: 対象ファイルのASTを解析し、`ast.NodeTransformer` によって安全なフォールバックへ書き換え。
3. **Hot-Reload / Circuit Breaker**: 修正直後の `compile()` による構文チェックと、エラー時の自動ロールバック。

以下は、`KeyError` に対して自動的に `.get()` フォールバックを適用する `NodeTransformer` の実装例です。

```python
import ast
from typing import Any

class ASTFallbackTransformer(ast.NodeTransformer):
    """
    例外発生行の代入文を、デフォルト値を返すように安全にラップ・置換する。
    """
    def __init__(self, target_lineno: int, fallback_value: Any = None):
        self.target_lineno = target_lineno
        self.fallback_value = fallback_value
        self.modified = False

    def visit_Assign(self, node: ast.Assign) -> ast.AST:
        if node.lineno == self.target_lineno:
            for target in node.targets:
                if isinstance(target, ast.Name) and isinstance(node.value, ast.Subscript):
                    self.modified = True
                    new_value = ast.Call(
                        func=ast.Attribute(
                            value=node.value.value,
                            attr='get',
                            ctx=ast.Load()
                        ),
                        args=[node.value.slice, ast.Constant(value=self.fallback_value)],
                        keywords=[]
                    )
                    return ast.Assign(targets=node.targets, value=new_value)
        return self.generic_visit(node)
```

## 開発現場の泥臭い苦労とアーキテクチャの進化

### 1. asyncioイベントループのブロック問題
ASTのパースやファイルIO、メモリ上でのAST変換はCPUバウンドかつ同期ブロックな処理です。これをFastAPIのメインイベントループ内で直接実行すると、他の全てのリクエストがストールしてしまいます。自己修復プロセス自体は `asyncio.to_thread()` や `ProcessPoolExecutor` にオフロードし、メインループの健全性を保つ設計が必須となります。

### 2. 複数行にまたがる式の処理限界
複雑なマルチライン例外に対して安全なAST置換を行うのは極めて困難です。ここで私たちは「何もしないことの勇気」を持ちました。無理に書き換えようとせず、複雑な箇所は安全にスキップして元の例外を流すフェイルセーフこそが、本番環境を守る品質です。

### 3. 二重防御のサーキットブレーカー
書き換えたソースコードは、必ずメモリ上で `compile()` を通して構文検証を行います。さらに物理ファイルへの書き込み時には `.bak` ファイルを作成し、ホットリロード後に別の例外が連鎖した場合は瞬時に元のコードへロールバックする機構を備えています。

## コードの価値から時間の価値へ

私たちが守りたいのは、単なる稼働率ではありません。深夜のプロセスダウンや不要なアラートを回避し、デバッグ時間をゼロに近づけること。そして何より、エンジニアの睡眠と本来の創造的な新機能開発時間を保護することです。

現実の泥臭いエラーログと向き合い、魔法に頼らない堅実な自己修復機構を構築することで、真の「時間の価値」を実現しましょう。
