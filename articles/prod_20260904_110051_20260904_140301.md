## 1. 限界稼働環境におけるアーキテクチャ原則：マイグレーション4フェーズ

論理レプリケーションを用いた無停止移行も選択肢にはあるが、我々のマルチテナント環境（テナントIDによる高密度な論理分離）においては、高負荷時のレプリケーションスロット肥大化リスクを避けるため、アプリケーション層またはDBトリガーによる「Dual-Write（二重書き込み）」アプローチを採用した。

巨大テーブルに対するスキーマ変更において、メタデータロックの専有時間をミリ秒単位に抑制するため、全工程を以下の4フェーズに厳格に分割する。

1. **Phase 1 (Schema Prep):** 
   - 新カラムを `NULL` 許容（または安全なデフォルト値付き）で追加。メタデータ変更のみで完了させ、既存データの書き換えを一切発生させない。
2. **Phase 2 (Dual-Write & Chunking):** 
   - DBトリガーを用いて、旧カラムへの書き込みを新カラムへも同時反映。それと並行し、バックグラウンドワーカーで過去データを分割移行（Chunking）する。
3. **Phase 3 (Cutover):** 
   - 読み込み先を新カラムへ切り替え、トリガーを無効化。
4. **Phase 4 (Cleanup):** 
   - 旧カラムの削除（`DROP COLUMN`）。本番負荷が極限まで落ちる深夜のメンテナンスウィンドウにてひっそりと実施する。

## 2. 実装パターン集：今すぐ現場で使える防衛コードスニペット

我々が血を流しながら獲得した、実戦投入済みのコードを提示する。

### 2.1 PostgreSQL: 排他制御を考慮したDual-Writeトリガー関数
マルチテナント環境において、トリガーの多重起動や無限ループを防ぎつつ、CPU負荷を最小限に抑えるPL/pgSQLの実装例だ。

```sql
-- Phase 1: 新カラムの追加 (NULL許容)
ALTER TABLE tenants_orders ADD COLUMN IF NOT EXISTS total_amount_v2 NUMERIC(12, 2);

-- Phase 2: 同期用トリガー関数の定義
CREATE OR REPLACE FUNCTION sync_orders_v2_trigger()
RETURNS TRIGGER AS $$
BEGIN
    -- マルチテナント環境におけるテナント分離を維持しつつ、無限ループを防止
    IF (TG_OP = 'INSERT') THEN
        NEW.total_amount_v2 := COALESCE(NEW.total_amount, 0.00);
        RETURN NEW;
    ELSIF (TG_OP = 'UPDATE') THEN
        -- 値に変更がある場合のみ同期 (CPUとWAL生成量の極小化)
        IF NEW.total_amount IS DISTINCT FROM OLD.total_amount THEN
            NEW.total_amount_v2 := NEW.total_amount;
        END IF;
        RETURN NEW;
    END IF;
    RETURN NULL;
END;
$$ LANGUAGE plpgsql;

-- トリガーの登録（既存トラフィックへの影響を最小限にするためROW単位で実行）
DROP TRIGGER IF EXISTS trg_sync_orders_v2 ON tenants_orders;
CREATE TRIGGER trg_sync_orders_v2
    BEFORE INSERT OR UPDATE ON tenants_orders
    FOR EACH ROW
    EXECUTE FUNCTION sync_orders_v2_trigger();
```text
### 2.2 PostgreSQL: デッドロックを防ぐ `SKIP LOCKED` チャンク移行クエリ
かつて我々は、過去データのバックグラウンド移行中に `deadlock detected` の嵐に見舞われ、APIからの書き込みトランザクションが次々と吹き飛ぶインシデントを経験した。
原因は、バッチ処理の `UPDATE` が広範囲の行ロックを取得しようとし、通常のWebリクエストと衝突したことだ。この悲劇を繰り返さないため、我々は `FOR UPDATE SKIP LOCKED` を標準化した。

```sql
-- 安全なチャンク移行クエリ（SKIP LOCKEDの活用 / チャンクサイズ200推奨）
WITH target_rows AS (
    SELECT id 
    FROM tenants_orders 
    WHERE total_amount_v2 IS NULL 
    ORDER BY id 
    LIMIT 200 
    FOR UPDATE SKIP LOCKED
)
UPDATE tenants_orders o
SET total_amount_v2 = o.total_amount
FROM target_rows t
WHERE o.id = t.id;
```text
### 2.3 Go言語: Thundering Herdを防ぐジッター付き指数バックオフ
DB側のロック競合が一時的に発生した際、クライアントやバッチワーカーが一斉にリクエストを再送すると、コネクションプールが瞬時に枯渇する「Thundering Herd（サバンナの暴走）」現象が起きる。これを防ぐためのGoバックエンド実装だ。

```go
package main

import (
	"context"
	"errors"
	"math/rand"
	"time"
)

// RetryWithJitter executes a database operation with exponential backoff and randomized jitter
// to prevent Thundering Herd problems during high-load cutover phases.
func RetryWithJitter(ctx context.Context, maxRetries int, baseDelay time.Duration, op func() error) error {
	var err error
	rng := rand.New(rand.NewSource(time.Now().UnixNano()))

	for attempt := 0; attempt < maxRetries; attempt++ {
		if err = op(); err == nil {
			return nil
		}

		if ctx.Err() != nil {
			return errors.Join(ctx.Err(), err)
		}

		multiplier := 1 << attempt
		backoff := baseDelay * time.Duration(multiplier)

		// Full jitter to prevent synchronized retry storms
		jitter := time.Duration(rng.Int63n(int64(backoff)))
		sleepDuration := (backoff / 2) + (jitter / 2)

		select {
		case <-ctx.Done():
			return errors.Join(ctx.Err(), err)
		case <-time.After(sleepDuration):
			continue
		}
	}
	return errors.New("max retries exceeded: " + err.Error())
}
```text

## 3. 永続プロジェクトとしての「保守・運用」の設計

1. **ORM自動マイグレーションの完全禁止:**
   - PrismaやTypeORM等の汎用ORMによる自動スキーマ同期（`synchronize: true` など）は、巨大テーブルに対して制御不能なロックを引き起こす。純粋なSQLスクリプト（FlywayやGolang-migrate等）による明示的かつ段階的な管理へ強制移行せよ。
2. **CI/CDパイプラインへのCustom SQL Linter導入:**
   - PR作成時に `ALTER TABLE ... NOT NULL DEFAULT` や、インデックスなしの一括 `UPDATE` を自動検知し、Exit Code != 0 でブロックするガードレールを敷くこと。
3. **緊急ロールバック手順（Runbook）の徹底:**
   - カットオーバー直後にデータ不整合やレイテンシ急上昇が起きた場合、数秒以内に切り戻すためのRunbookをチームの魂に刻み込め。
