## 大規模Webサービスを死守せよ：DBコネクションプール枯渇とリトライストームの泥沼から生還する実戦アーキテクチャ

バックエンドを統括する中で、我々の使命は単に仕様通りに動くコードを書くことではない。極限のトラフィック下でも決して沈黙せず、開発チームの時間と精神を死守する堅牢なアーキテクチャを構築することだ。

今回は、幾度となく直面し、泥臭く乗り越えてきた「DBコネクションプールの枯渇」と「リトライストーム」という雪崩式障害（Snowball Effect）に対する、実戦的な防衛レシピを公開しよう。魔法のツールではなく、物理法則に基づいた生存戦略と知見を共有する。

## なぜ、あの夜あなた達は泥沼にハマったのか？

深夜3時のページャー、無限リトライの嵐、そしてログに刻まれる絶望のメッセージ。


たった1本、インデックスが欠落したスロークエリが混入したとする。それが引き金となり、一瞬にしてコネクションが占有され、プールが枯渇する。エラーを検知したフロントエンドやAPIクライアントは律儀にリトライストームを開始し、PostgreSQLは悲鳴とともに沈黙する。

この連鎖的な死に直面したとき、未知のハングアップの原因特定に、エンジニアはどれほどの時間を奪われてきただろうか。我々が構築すべきは、この数時間のデバッグ地獄を「数秒の自動フォールバック」へと置換する機構である。

## アプリケーション層：魔法ではなく物理で殴る遮断機構

無限リトライという名の意図せぬDDoS攻撃を根絶するには、独立型のサーキットブレーカーと、ジッター（揺らぎ）を伴う指数バックオフの実装が不可欠だ。

```typescript
// circuitBreakerPoolGuard.ts
import { Pool } from 'pg';

interface CircuitBreakerOptions {
  failureThreshold: number;
  successThreshold: number;
  cooldownPeriodMs: number;
}

class DatabaseCircuitBreaker {
  private state: 'CLOSED' | 'OPEN' | 'HALF-OPEN' = 'CLOSED';
  private failureCount = 0;
  private successCount = 0;
  private nextAttemptTimestamp = 0;

  constructor(private options: CircuitBreakerOptions) {}

  public async execute<T>(queryFn: () => Promise<T>): Promise<T> {
    if (this.state === 'OPEN') {
      if (Date.now() < this.nextAttemptTimestamp) {
        throw new Error('CIRCUIT_OPEN: DB protection mode active. Fast-failing request.');
      }
      this.state = 'HALF-OPEN';
    }

    try {
      const result = await queryFn();
      this.onSuccess();
      return result;
    } catch (error) {
      this.onFailure();
      throw error;
    }
  }
  
  private onSuccess() {
    this.failureCount = 0;
    if (this.state === 'HALF-OPEN') {
      this.successCount++;
      if (this.successCount >= this.options.successThreshold) {
        this.state = 'CLOSED';
        this.successCount = 0;
      }
    }
  }

  private onFailure() {
    this.failureCount++;
    if (this.state === 'HALF-OPEN' || this.failureCount >= this.options.failureThreshold) {
      this.state = 'OPEN';
      this.nextAttemptTimestamp = Date.now() + this.options.cooldownPeriodMs;
      this.successCount = 0;
    }
  }
}

export async function queryWithBackoff<T>(pool: Pool, queryText: string, params: any[], retries = 3, baseDelayMs = 200): Promise<T> {
  const breaker = new DatabaseCircuitBreaker({
    failureThreshold: 5,
    successThreshold: 2,
    cooldownPeriodMs: 10000,
  });

  let attempt = 0;
  while (true) {
    try {
      return await breaker.execute(async () => {
        const client = await pool.connect();
        try { 
          return await client.query(queryText, params); 
        } finally { 
          client.release(); 
        }
      });
    } catch (error: any) {
      if (error.message.startsWith('CIRCUIT_OPEN')) throw error;
      
      attempt++;
      if (attempt > retries) throw new Error(`Max retries exceeded. Last error: ${error.message}`);

      const jitter = Math.random() * 100;
      const delay = Math.pow(2, attempt) * baseDelayMs + jitter;
      await new Promise(resolve => setTimeout(resolve, delay));
    }
  }
}
```

ここで重要なのは「ジッター（揺らぎ）」だ。乱数を加えることで再試行の波を時間軸上で分散させ、データベースがリカバリするための隙間を意図的に作り出す。

## インフラ・コネクション層：「とりあえず増やす」愚策からの脱却

プール枯渇に直面した際、サイズを闇雲に増やすのは最悪のアンチパターンだ。物理限界を無視した設定は、コンテキストスイッチのオーバーヘッドを生む。プールサイズは原則として「CPUコア数 × 2 + 有効ディスクI/Oスレッド数」という物理的根拠に収束させるべきだ。

また、リーク検出の閾値を設け、接続を握りしめたまま返却しないコードパスのスタックトレースを強制的に吐き出させる水際対策も忘れてはならない。

## データベース層：DB自身によるハードリミット

アプリケーション側をどれだけ堅牢に設計しても、アドホックなクエリやバグによる無限ループからDBを守るためには、DBセッション自体にハードリミットを設ける必要がある。

```sql
SET statement_timeout = '3s';
SET idle_in_transaction_session_timeout = '5s';
```

3秒以上応答しないクエリは無慈悲にKillする。部分的なエラーを許容し、システム全体の死を防ぐ。これが「全体を生かすためのフェイルファスト」の真髄だ。

## まとめ

システムを死守することは、エンジニアの時間を死守することと同義だ。堅牢なアーキテクチャの構築を通じて、泥臭くも圧倒的な技術的知見を磨き続けよう。
